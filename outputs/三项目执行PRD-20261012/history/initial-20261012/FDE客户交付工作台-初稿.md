## 3. 一条完整流程：虚构“独立站＋AI文件处理”

**样例只用于设计和未来隔离验收，不是现有真实客户资料。**

> 虚构企业“青禾样例商贸”，8人团队。想建独立站展示约20个产品并接收咨询；销售每天手工整理供应商PDF报价，希望AI提取产品名称、规格、数量、单价和币种，形成可核对表格。业务人员要人工确认结果。语言、文件是否扫描件、资料授权、域名、负责人、预算、维护和上线时间尚不明确。

| 步骤 | Eli的操作 | 可检查输出与边界 |
|---|---|---|
| 1 选原文 | 在既有后台选一份需求的提交版本v1，进入交付页；有未提交草稿时提示先提交或另存为原文版本 | 固定`intakeId/submissionId`及原文副本；之后原问卷补充不静默覆盖本工作台来源 |
| 2 补关键问题 | 从规则建议中选入、调整问题，并记录答复及依据 | Q-01语言、Q-02文件类型、Q-03数据授权、Q-04人工审核角色等；关键项标“阻断范围/报价”，一般问题可后置 |
| 3 整理范围 | 将原话拆成R-01产品展示、R-02咨询入口、R-03文件字段提取试验；分别标“候选/确认记录/后置/不做” | 独立站候选交付物、内容准备责任；AI处理条件仍待验证。线上支付、账号体系、自动改价、自动外发先列不做；不能从“独立站”推断需要全套电商 |
| 4 准备报价 | 建范围基线S1，给阶段条目填写工时区间、费率、已知外部成本；未填项保持待估 | E1只引用S1。资料不足可先列“范围梳理”“网站首版”“文件处理可行性试验”，不生成真实市场价或总承诺 |
| 5 记录变更 | 收到“再加付款功能”的假设补充，记录变更C-01、原因、影响及是否采纳 | 未采纳不进入基线；采纳须Eli记录人工决定及依据，并产生S2，提醒E1与S2不一致；不把C-01直接标为免费包含 |
| 6 准备和记录验收 | 给每个进入基线的条目补验收动作与证据要求，记录实际结果 | 网站“可查产品/提交咨询”；AI试验“固定虚构样例字段核对、人工复核、异常样例标记”，可填未测/通过/未通过/不适用。原型演示不证明真实AI提取能力 |

首版交付的是管理上述资料的软件。它不会在本工作台内建设独立站、上传解析PDF、训练模型或执行客户项目；样例中的交付承诺和数值仍由Eli另行确认。

## 5. 页面、状态与信息架构

保留`/`原问卷、`/guide`、登录及原后台列表/详情。建议仅新增`/admin/intakes/:id/delivery`，原详情增加“交付资料”入口；六段为来源与问题、范围、报价、变更、验收、版本/导出，桌面主编辑区＋简短摘要，390px按段顺序阅读。Eli的主任务是填写和核对，不需要复杂看板。

| 状态/异常 | 要求 |
|---|---|
| 无工作台/未提交原文 | 指明先选提交版本；保留原问卷草稿，不自动帮客户提交 |
| 加载/空段/有未保存修改 | 加载与占位区分；空段允许手工填写；显式保存，离页前提示，成功响应前不显示已保存 |
| 原文新补充/范围版本不一致 | 提醒新旧来源或基线；不自动合并，也不把旧报价改成当前版本 |
| 保存失败/401/409/请求超时 | 编辑内容留在当前页；重新登录或读取新revision后核对，不能静默重试覆盖。未知提交结果用原请求键核实，不另生成重复版本 |
| 400/413/数据库不可写 | 按字段提示或限额提示，不报成功，不部分记录采纳结果；不扩大现有48KiB请求上限来掩盖无界输入 |
| 来源缺失/备份不配套 | 工作台只读且提示所缺ID，不能借相似名称把资料绑定到另一个客户 |

建议限额：单份100条需求、100个问题、30个报价阶段、100条变更、200条验收，每条长文本最多2000字；修改按单段/单事件提交，不把整个历史塞进写请求。具体服务端schema须在实施时落地并测试。所有按钮提供明确标签、键盘焦点、禁用/进行中状态，错误不只靠颜色。

## 6. 数据、版本、金额与权限

### 保护旧数据的存储建议

推荐复用现有Express鉴权，在现有`DATA_DIR`下**新建独立`delivery.sqlite`**，旧`intake.sqlite`表和已有问卷字段不修改；避免把交付结构塞入备注自由文本。新库和目录沿用本机600/700权限。此为未来设计，当前没有创建、打开或读取任何数据库。

新库仅在获准实施的显式初始化步骤创建；正常运行发现它缺失或损坏时，不能自动重建空库冒充恢复。初始化失败保留现场，新交付模块不可用不应阻断既有问卷。

不选重写前端/换框架/迁移云数据库；不采用localStorage作为工作台持久源；不覆盖原始回答来表达项目确认。SQLite仍仅针对本机单人，不能推出生产容量结论。独立库的代价是双库备份及引用核对，已纳入A07和12小时预算；若未来选择往旧库加表，需另有对该migration的具体授权与恢复方案，不能默认替换此路线。

| 核心对象 | 最小字段/约束 |
|---|---|
| Workspace | UUID、唯一intakeId、revision、sourceSnapshot、当前范围/报价/验收版本引用、各编辑段、创建/更新时间；创建须经服务端核对原记录存在 |
| SourceSnapshot | submissionId、原文version、必要回答副本、actor/time、内容校验值；不复制能力凭证、登录信息；明确是客户原文而非Eli确认 |
| Question/Requirement | 稳定itemId、内容、来源定位、事实/假设/待问标记、处理状态、负责人；确认记录有依据、记录人和时间，不能靠模型填值 |
| DeliveryVersion | UUID、workspaceId、kind（来源/范围/报价/验收）、递增version、前版ID、基线引用、完整JSON payload、schemaVersion、templateVersion、actor/time、requestKey；版本不可改写 |
| Change/Event | UUID、workspaceId、baseScopeVersion、提出/决定及影响、依据、服务器actor/time、requestKey；同一采纳请求仅一次。附加审计只记录动作/对象，不存秘密或全文 |

新库内部用外键和唯一约束；两库间不能假设有自动外键。引用同时保存不可变原文副本，读取时核对intakeId/submissionId；旧原文不可删除的既有边界继续适用。原文更新、新基线和Eli记录确认都属于不同事件。原`intakes.stage`保持原语义，不能代替“范围已确认/项目已验收”。

建议新API统一放在`/api/admin/intakes/:id/delivery`下，另设版本、事件、导出子资源。复用`auth`/CSRF、Origin、Host、输入限制与错误返回；服务端校验子对象归属，严格白名单拒绝伪actor、跨客户ID和任意文件路径。不开放客户侧delivery API。报价/变更/范围的依赖校验、版本插入与当前引用更新在新库同一事务内完成。

### 报价草案规则

- 工时按整数分钟保存上下界，费率与成本以最小货币单位整数保存；币种由Eli明确选择，首版限定CNY/USD/EUR的一种，不跨币种求和或换汇。
- 阶段工时金额上下界分别为`roundHalfUp(分钟 × 每小时费率 / 60)`；对每阶段先取整，再加Eli明确录入的外部成本，最后累加阶段金额；应提供计算例单元测试。
- 空值代表待估，不代表0。免费/零成本须Eli主动输入0并说明；成本“不适用”也是显式状态。任一包含条目金额或成本状态未齐，整体总额为“待估”，可显示“已填写部分小计”，不能包装成总报价。
